# Marketchecker

Веб-апликација (PWA, за мобилен) што секој ден ги чита јавните ценовници на
маркетите во Македонија и на корисникот му ги прикажува **само производите на
попуст** — за неговиот град, неговите маркети и категориите што ги следи.

Цените се **по продавница**, не по синџир: ист производ во две продавници на
истиот маркет може да има различна цена.

## Технологии

Python 3.12 · FastAPI · PostgreSQL 17 · SQLAlchemy 2 (async) + Alembic ·
httpx · selectolax / BeautifulSoup · pdfplumber · Jinja2 + HTMX ·
APScheduler · Docker Compose · pytest · ruff

## Стартување

```bash
cp .env.example .env          # па смени ги POSTGRES_PASSWORD и SECRET_KEY
docker compose up -d db
docker compose run --rm api alembic upgrade head
docker compose up -d api

# прочитај ги ценовниците и запиши ги попустите
docker compose exec api python -m app.cli citaj

# или само неколку продавници, за проба
docker compose exec api python -m app.cli citaj --ramstore --limit 2

# состојба за денес: кој извор поминал, кој паднал
docker compose exec api python -m app.cli izvestaj

# дневно читање во 11:00, автоматски
docker compose up -d scheduler
docker compose logs -f scheduler
```

Апликацијата е на <http://localhost:8000> (API документација на `/docs`).
Без читање базата е празна и страницата нема што да прикаже.

Нема најава: се отвора страницата и се гледаат сите денешни попусти.
Филтрите (град, маркет, група, подредување) се во URL-то, за да може линк
да се подели. `/sostojba` покажува кое читање поминало, а кое паднало.

Ако портот 5434 (Postgres) или 8000 (апликација) е зафатен, смени
`POSTGRES_HOST_PORT` / `APP_HOST_PORT` во `.env`.

### Тестови и lint

```bash
docker compose run --rm api pytest
docker compose run --rm api ruff check .
```

Тестовите се вртат врз **зачувани примероци** во `backend/tests/fixtures/`,
никогаш врз живи сајтови. Тестовите што бараат база се означени со
`@pytest.mark.db` и се прескокнуваат ако базата не е достапна.

### Нова миграција

```bash
docker compose run --rm api alembic revision --autogenerate -m "опис"
docker compose run --rm api alembic upgrade head
```

Табелите ги создава **само** Alembic. Апликацијата никогаш не вика
`create_all()`.

## Како се групираат производите

Првата верзија **не** бара од корисникот да избира што следи: ги прикажува
**сите денешни попусти**, подредени по неколку груби групи на употреба —
храна, пијалоци, козметика, хигиена за дом, бебе, миленици, и така натаму.

Ситните категории („маслиново" наспроти „сончогледово масло") чекаат додека
не се види што бараат корисниците. Причината е практична: ценовниците се
полни со производи каде истиот збор значи различни работи —

```
МАСЛА ЗА ЈАДЕЊЕ - МАСЛО ЗА ЈАДЕЊЕ МАСЛИНОВО   → храна
КОЗМЕТИКА ЗА ГЛАВА - БОИ ЗА КОСА ЗА ЖЕНИ      → козметика
САДОВИ ЗА МАСЛО И ОЦЕТ                        → дом
```

Групата се чита од **описот** во ценовникот (полицата на која стои
производот), а називот служи како резерва. На податоците од 2026-10-02 тоа
сортира **94%** од попустите; останатите одат во групата „Друго" и **сè уште
се прикажуваат**. Што останало несортирано се гледа со:

```bash
docker compose exec -e PYTHONPATH=/app api python scripts/report_groups.py /tmp/opisi.json
```

## Дневно закажување

Контејнерот `scheduler` ги чита сите ценовници **секој ден во 11:00**
(Europe/Skopje). Часот се менува со `SCHEDULER_HOUR` / `SCHEDULER_MINUTE`,
а се гаси со `SCHEDULER_ENABLED=false`.

Зошто 11:00: Рамстор ажурира во 4:00, КАМ околу 5:50, Веро околу 7:00.

Три работи што ги прави сам:

- **Не чита двапати истовремено** — ако претходното читање сè уште трае,
  новото се прескокнува.
- **Не го губи денот поради доцнење** — пропуштен термин може да почне и
  до 6 часа подоцна.
- **Надокнадува пропуштен ден** — ако контејнерот бил спуштен во 11:00 и
  се крева во 15:00 без читање за тој ден, чита веднаш. Ако веќе има
  читање, не повторува.

Читањето трае околу 20 минути: синџирите се читаат напоредно, но Веро има
21 страница по продавница и паузата меѓу барања се почитува. Ценовник со
иста содржина како претходно се прескокнува, па повторните читања се брзи.

## Што се чува

Три табели со различна намена и различен раст:

| Табела | Што | Раст |
|---|---|---|
`current_price` | цената на **секој** производ во секоја продавница | ~250 MB, **не расте** — се пребришува |
`price_change` | запис **само кога цената се смени** | ~10–15 MB дневно |
`price_row` | дневните попусти (ова го чита страницата) | ~15 MB дневно |
`daily_store_stats` | збир по продавница и ден | 153 реда дневно |

Зошто вака: 1,5 милиони реда дневно би биле **310 MB дневно** ако се
чуваат сите состојби, а 99% од тоа се идентични редови — млекото чини
исто и вчера и денес. Со чување на промените наместо состојбите,
историјата останува мала, а „колку чинеше ова пред месец" и натаму има
одговор.

Чувањето на целиот асортиман (не само попустите) е потребно за две
работи: **корпа** („јајца, млеко и леб — каде е најевтино вкупно") и
**статистика** („кој маркет има најголеми попусти"), зашто бројот на
попусти без асортиман не значи ништо.

Историјата се чисти по **две години**, автоматски по секое дневно читање.
`daily_store_stats` НЕ се чисти — мала е, а токму таа ја носи
долгорочната слика.

```bash
docker compose exec api python -m app.cli statistika
docker compose exec api python -m app.cli isчisti    # рачно чистење
```

## Правила

- **Попуст** = ред со пополнета цена со попуст. **Еднодневен** = датум од
  == датум до.
- Производот се прикажува **точно како во ценовникот**, со бренд и грамажа.
  Nescafe 100 g и Nescafe 200 g се различни производи.
- „Лојалност" (само со картичка) се означува одделно од обична акција.
- **Учтиво читање**: пауза меѓу барања, повторни обиди, јасен User-Agent.
- Ако структурата на ценовник се смени, читачот **јавува грешка** и се
  логира — никогаш тивок празен резултат.
